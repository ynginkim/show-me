# 강의·발표 자료 mode

말로 설명하기 전에 실물을 보여 주는 강의 자료를 만들고, 찍은 화면으로 판정한다.

이 mode는 요청과 프로젝트 상태를 보고 playbook 하나를 고르고, 단계마다 leaf skill을 읽어 그 결과로 다음 단계를 정한다. leaf는 맡은 결과와 검사 근거, 남은 문제를 돌려주면 끝난다. 반복·재실행·중단은 playbook이 정한다. 다른 skill은 이 mode 폴더의 형제 폴더에 있는 SKILL.md를 직접 읽는다. 도구 경로와 공유 계약은 `../resolve-show-me-tools/SKILL.md`가 정한다.

## 결과물과 판정

| 구분 | 계약 |
| --- | --- |
| 결과물 | 덱 프로젝트 폴더. 발표에 들고 가는 `slides/`(index.html, deck.css, scenes.js, engine/, fonts/, media/)와 `talk.md`, `qa/deck/report.md`·`sheet.png`, `제작노트.md` |
| 에이전트 완료 | `check_deck.py`의 자동 검사 실패 0(페이지·콘솔 오류, 없는 파일, 깨진 미디어, 예산 초과, 설정 오류). 경고는 처리하거나 이유를 남겼다. `sheet.png`·`sheet_interactions.png`와 글이 많은 장을 Read로 열어 봤다. 현장 전용 자료 목록과 재생성 명령을 제작노트에 남겼다 |
| 사람 판정 | 발표할 화면에서의 맨 뒷줄 가독성과 색, 리허설로 잰 구간별 시간, 영상 소리, 내용·말투가 청중에게 맞는지 |

납품 보고 끝에 다음 문장으로 사람 판정을 요청한다. 끝내지 못한 항목은 이 문장 앞에 따로 적는다.

> `slides/index.html`을 발표할 화면에서 열어 F(전체 화면)·T(타이머)로 한 번 넘겨 보며 리허설해 주세요. 저는 1920×1080 스크린샷과 오류 검사로 확인했고, 현장 화면의 글자 크기와 소리, 실제 말하는 시간은 확인하지 못했습니다.

검사 스크립트의 exit 0만으로 완료라고 쓰지 않는다(**principle-judge-from-shots**).

## 브리프

사용자와 맞추는 것은 **의도**다. 계획(구성·장 목록·설계)은 맞추지 않고 이 mode가 정한다.

- **의도:** 누구에게(청중, 사전 지식, 인원), 무엇을 전하려는지(듣고 나서 남을 한 가지), 강조할 것과 뺄 것, 공개 범위(현장 전용인지 공유할 자료인지).
- **사실:** 강의 길이와 질문 시간, 장소·화면(프로젝터·모니터, 발표 컴퓨터), 자료 위치(녹화·캡처·링크·영상 프로젝트).
- 이 가운데 요청과 파일에 없는 것만 처음에 한 번 묻는다.
- 답을 받으면 이해한 의도를 3~5줄로 되짚어 보이고, 어긋남이 있을 때만 고친다. 사용자가 이미 분명히 말했으면 되짚기도 짧게 한다.
- 구성, 장 수, 장 순서, 색, 부품, 애니메이션은 묻지 않고 근거를 붙여 정한 뒤 `talk.md`와 보고에 적는다. `talk.md`를 보여 주고 승인을 기다리지 않는다.
- 사용자가 "먼저 계획을 보여 달라", "바로 고치지 말고 알려 달라"고 명시하면 그때만 계획을 먼저 보이고 기다린다.
- 작업 폴더의 정책(프로젝트 폴더 위치, 기록 파일)이 있으면 그것이 먼저다.

이 구분은 2026-11-26 사용자 피드백에서 왔다. "내 의도만 명확하게 전달되면 어떻게 강의자료를 구성할지는 AI가 알아서 하는 게 더 좋다"

## 진행 방식 선택

| 요청과 상태 | playbook |
| --- | --- |
| 새 강의·발표 자료. 녹화·캡처 같은 원자료나 Lightplay 영상 프로젝트에서 출발해도 같다 | `playbooks/create-deck.md` |
| 이미 만든 덱 프로젝트(`slides/index.html`이 있다)의 문구·장·순서·시간·미디어·엔진을 고친다 | `playbooks/revise-deck.md` |

맞는 흐름이 없으면(예: PPTX 파일만 원함, 영상만 원함) 범위 밖이라고 말하고 멈춘다. 영상이 필요하면 Lightplay의 showreel-mode로 따로 만들고, 이 mode 안에서 그 mode를 부르지 않는다. 한 번 찾아보면 끝나는 질문이나 오타 한 곳 수정은 playbook 없이 처리하고 `check_deck.py`만 다시 돌린다.

고른 playbook을 끝까지 읽는다. 줄 맨 앞에 `1. `처럼 번호가 있는 단계 문장만 그대로 todo 첫 항목들로 복사하고, 그 뒤에 이 작업의 세부 항목을 붙인다. todo 도구가 없으면 응답 첫 줄 `단계 n/N:` 다음에 원문을 번호 목록으로 쓴다. 실행하지 않는 단계도 지우지 않고 `skip: 이유`를 남긴다.

## 진행 장부와 운영

진행이 길어지면 프로젝트 폴더에 `PAUSE.md`(끝난 것, 진행 중인 것, 다시 시작하는 명령)를 남긴다. 긴 영상 변환은 백그라운드로 돌리고 그동안 본문을 쓴다. 정해진 시간만큼 잠들어 기다리지 않는다.

## 경계

- 원자료와 Lightplay 프로젝트는 읽기만 한다. 변환본과 사본은 덱의 `slides/media/`에 두고 출처를 `media.json`에 남긴다.
- 실제 고객·동료·가족 화면처럼 공개 범위가 걸린 자료는 `--onsite`로 기록하고, 덱을 공개 게시하거나 예제·템플릿으로 재사용하지 않는다(**principle-show-the-real-thing**의 Stop).
- 엔진(`slides/engine/`)은 고치지 않는다. 덱에 필요한 동작은 `scenes.js`에 쓴다(**principle-content-before-engine**).
- 사용자가 요청하지 않으면 commit·push·외부 게시·전역 설치를 하지 않는다. playwright-core 설치와 글꼴 내려받기는 네트워크를 쓰므로 처음 한 번 알리고 진행한다.

## Principles

- **청중의 말로** (`principle-audience-words`). 슬라이드 제목·라벨·설명을 쓸 때 내부 이름과 도구 용어 대신 청중이 아는 말을 고른다.
- **실물로 보여 주기** (`principle-show-the-real-thing`). 장마다 설명 방식을 고를 때 녹화·캡처·링크를 먼저 고르고, 보이지 않는 과정만 도식으로 그리며, 공개 범위가 걸리면 현장 전용으로 표시한다.
- **내용이 먼저, 엔진은 나중** (`principle-content-before-engine`). 새 동작이 필요할 때 덱의 scenes.js에 먼저 쓰고, 두 번째 덱이 같은 것을 필요로 할 때 엔진으로 올린다.
- **찍은 화면으로 판정** (`principle-judge-from-shots`). 완료와 수정 범위를 정할 때 HTML 소스나 종료 코드가 아니라 찍은 화면·검사 표·수정 전후 비교로 판단하고, 현장 확인은 사람에게 남긴다.

보고에는 적용한 principle 이름과 그것이 바꾼 결정 하나를 남긴다. 읽지 않은 principle은 인용하지 않는다.
